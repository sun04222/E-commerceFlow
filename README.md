# E-commerceFlow · 电商售后处置 Agent 演示工程

面向电商售后场景的一个演示实现：输入客户的自然语言消息后，依次完成咨询理解、问题分类、取证与单据处理、判责、只读复核、授权审批、结单回执。全套流程可以运行、回放，并用回归样本校验行为是否符合预期。

工程参考 Craft Agents（craft-agents-oss）的架构思路进行自建，核心包括统一命名空间的工具面、按环节动态装配、三档授权闸、审批回调回路、三层渐进式上下文披露、只读 Reviewer、决策轨迹（JSONL）与三级样本回归门禁。整个工程不依赖任何第三方库。

- **取证环节在结构上摸不到可执行工具**：装配层只返回只读查询，出现可执行工具直接抛错——不是「提示词请勿执行」，是「拿不到」
- **授权跟着金额走，不跟工具走**：同一把 `aftersales.decide_refund`，49.90 直接执行、389 先问人、1299 挂起等审批（Agent 无权执行）
- **门禁可证伪**：`--ablation` 摘掉 Reviewer 后 M07 立刻放行，8 样本门禁 8/8，任一行为偏移退出码即 1

## 快速开始

```bash
node src/cli.ts --demo --offline      # 8 条合成咨询走完整六步链路
node src/cli.ts --gate --offline      # 回归门禁：8/8 才退出码 0
```

零安装、零 `npm install`（Node ≥ 22.18 直接跑 `.ts`）；不想装 Node 就双击根目录 `demo.html`——单文件、断网可用。完整命令清单见下方「命令详解」。

## 项目背景

**问题背景。** 在电商售后流程中，从客户提出诉求到资金真正退还，中间需要经过取证、判责、复核、审批四个环节。全程人工处理较慢，且不同处理人员的口径难以统一；若完全交给大语言模型自由发挥，容易出现两类风险：应当核查的关键证据没有核查，以及应当拦截的操作没有被拦截。

**设计思路。** 本工程把「Agent 能做什么」作为结构性约束来实现，而不是写进提示词。取证环节只暴露只读查询工具（由装配层决定，而非提示词约定）；金额超过阈值时流程自动挂起、等待人工审批（Agent 在结构上无权执行）；复核结论不通过则回退重新处理，而不是由模型自行确认。这些约束都落在可被代码校验的位置，并用回归门禁加以验证——用 8 个样本跑一遍，若任一行为偏离预期则退出码为非零。

**适用形态。** 项目提供三种使用方式，按不同需求选择：`demo.html` 为单文件演示版（双击即可运行，无需安装）；`src/` 与门禁适用于需要运行、修改并验证行为的开发者；接入真实平台时可看 `data/connectors.json`（接入新平台只需修改声明，前端与引擎无需改动）。

**关于离线模式。** `--offline` 下规则判定与模型判定走同一条链路，仅判据来源不同。没有配置密钥也能端到端跑通并通过门禁，验收不依赖任何外部服务；因此拿到工程的人无需先准备 API key 即可查看效果。

## 桌面端 · 售后 Agent · 自主处置台（对话式自主执行）

不想看命令行，就用自主处置台：Windows 双击项目根目录的 **`启动桌面端.cmd`**（自动找 Node → 起本地服务 → 用 Edge 以无边框 `--app` 模式打开独立桌面窗口）；macOS / Linux 跑 **`./启动桌面端.sh`**。**不需要 npm install**；规则判定不需要联网，**模型判定才需要联网**。服务只绑本机 `127.0.0.1`，别的设备连不上——要在别的设备上看，发 `demo.html` 单文件版。

> 对方机器上没有 Node 22.18？别折腾环境，直接发 `demo.html` 单文件版（见上一节）。

```
启动桌面端.cmd
├─ node desktop/server.mjs            # 零依赖 HTTP 服务，动态 import src/*.ts
└─ msedge --app=http://127.0.0.1:8787 # 独立应用窗口，关窗口即退出演示
```

也可以手动起服务再用任意浏览器开 `http://127.0.0.1:8787`（端口可用 `PORT=9000 node desktop/server.mjs` 覆盖）。

> **启动器为什么是英文界面？不是偷懒。** `启动桌面端.cmd` 里刻意一个中文字符都没有：批处理文件由 cmd 按当前控制台代码页逐字节解析，编码与代码页对不上时，多字节汉字会被拆错、甚至吞掉换行符，把后面的行当成独立命令执行——实测表现就是**服务起不来、窗口打开是空白**。在文件里写 `chcp 65001` 也救不了：`chcp` 之后 cmd 的**行解析会错位，紧跟着的那一行会被丢掉**（已用最小 5 行用例复现，详见 `docs/04` 第七节）。所以取舍是：文件纯 ASCII + 说明文字用英文，可靠性优先。`启动桌面端.sh`（macOS / Linux）不受影响。

**这一版是「对话式自主执行」形态，不是结果看板**：贴一句客户原话 → Agent 自己跑完六步 → 直接执行处置或停办转审批。默认**全程不打断人**，只有超出自主边界的资金动作才会生成一张审批卡等人裁决。

**首屏不介绍自己，只放当下要做的事**：左栏是处置队列与示例，中间是工作台——「数据已接入 / 等你拍板 / 最近的处置」三块，全部是实时状态与可点入口；输入框就在底部。成熟的产品不需要先在首页讲一遍自己能干什么，直接让人开始用。

**自主边界（写在界面上，不是隐藏逻辑）**：

| 金额 | 处置档位 | Agent 的行为 |
|---|---|---|
| 不涉及资金 / 只读查询 | 零打扰 | 直接跑完，不进审批 |
| ≤ ¥100 | 直接执行 | 自主执行，不打扰人 |
| ≤ ¥500 | 自动确认后执行 | 自主确认并执行 |
| > ¥500 | **人工审批** | 停办、生成审批卡，等人裁决后自动续办结单 |

顶栏有常驻的**「自主执行」开关**：关掉之后，原本自动执行档的案件全部转入人工审批队列。

**界面结构**（深色图标轨 + 三栏）：

| 区域 | 内容 |
|---|---|
| 顶：监管指标条 | 已自动处理 / 待人工审批 / 已拦截 / 审批未通过 / 需补充信息 / 未跑通——**每一项都可点**：点一下按该状态筛左侧队列并自动选中第一条（右栏立刻给出结论与可复制的客户回复）；点「待人工审批」直接进审批中心；再点一次取消筛选。数字由结果状态机实时推导 |
| 顶右：判定引擎 + 命令面板 | 显示当前用「智能模型判定」还是「内置规则判定」，**可点切换**（有密钥时）。旁边是 **Ctrl / ⌘ + K 命令面板**（见下「键盘」） |
| 左：深色图标轨 | 今日处置 / 人工审批（带待办角标）/ **数据源** / 接口设置 / 新建处置；窗口变窄时另出现两个**抽屉入口**（见下） |
| 左二：今日处置队列 | **搜索框**（客户原话 / 案件类型 / 单号 / 处理结果，多个词逐个命中）+ 状态筛选标签；不筛不搜时按**等你处理 / 正在处理 / 已自动完成**分组——日常就这两堆事。条目带时间、状态徽章与跟进标签（跟进标签本身就是入口，点了直接落到**那一条**的跟进面板）+「示例」8 条预置客户原话 |
| 中：主区 | 首屏是工作台；选中记录后是一条从上到下的判断链：客户原话 → **结论卡**（一句话说清办完没有 + 金额 + 该点的那个动作）→（停办时）**内联审批卡** → **执行过程时间线** → 结果详情与给客户的回复 → 底部输入框。切「人工审批」是待审队列，切「数据源」是数据接入页 |
| 右：处置详情 | 选中某条时：当前状态 / 案件类型 / 处理结果 / 合规复核意见 / 它拿不准的地方 / 自主边界（是否问了人、调取过哪些资料、复核补了几轮取证）/ 人工跟进台账 / 给客户的回复。**没选中时不再是空白**：改为「处置概览」——三块可点数字（已自动处理 / 待你拍板 / 待你接手）+ 每行入口。在「数据源」页右栏改为显示取数通道与库内规模 |

**执行过程是一条一条长出来的，不是把结果分几拍点亮**：六步时间线（理解需求 → 核实订单 →
拟定方案 → 合规复核 → 授权与执行 → 回复客户）由引擎的**轨迹事件**驱动——每落一步，那一行当场
出现它的真实动作、真实时长与过程记录（可展开看依据与逐条记录）。为此服务端新增
`POST /api/run/stream`（NDJSON：先 `start`，再逐条 `event`，末尾 `result`）；单文件版没有网络，
但引擎就在同一个页面里跑、回调是真发生的，接的是**同一份 `onEvent`**——界面代码只有一套。
上一版那句「不编一个进度条」依然成立，而且更硬：现在显示的进度不是编的，是引擎自己的审计轨迹。

**结论在前、过程在后**：打开一条案子，第一眼是「这事办完了没有、多少钱、下一步点哪」；
想看它凭什么走到这一步，往下翻就是六步与逐条记录。**停办等人的案子更靠前**——审批卡紧跟在结论
下面：它等的就是人，让人再往下滚一屏才找到裁定按钮，等于没做这件事。

**审批做成消息块，不把人打发到另一个页面**：超出自主边界的处置就地生成一张审批卡（四问：
为什么停下来 / 依据是什么 / 拿不准的地方 / 批准与驳回分别会怎样）。批准即真执行并自动结单，
驳回即如实收口未执行，两条路都不需要再点第二次；续办句柄没了的单子不给假按钮，只给「重新处置」。
审批中心页仍在，用于看全量待审队列。

**键盘走得通**（这一层上一版是整层留白，本版补上）：

| 键 | 作用 |
|---|---|
| `Ctrl / ⌘ + K` | 命令面板：动作 + 处置记录 + 示例场景合成**同一份可搜索列表**；Tab 在面板内循环，Esc 关闭后焦点回到打开它的入口 |
| `/` | 光标进客户原话输入框 |
| `j` / `k` 或 `↓` / `↑` | 在队列里上下移动并预览，`Enter` 打开 |
| `1`–`6` | 按顶部指标筛选，再按一次取消 |
| `?` | 快捷键一览 |
| `Esc` | 关掉面板或抽屉 |

**界面里不提供金额动作的快捷键**：批准 / 驳回只能在那张写着四问的卡上做出。这不是没做完，
是不想把一笔退款变成一个两字母的误触。无障碍是实测过的而不是声明：所有可交互元素都有可访问名
（实测 55 个、0 缺失）、装饰性图标全部 `aria-hidden`、结论与审批结果走 `aria-live` 播报、
抽屉打开时才有 `role=dialog` + `aria-modal` 且焦点进入、关闭后焦点还给入口；正文与辅助文字在
浅/深两套主题下都达到 WCAG AA（`--ink-3` / `--ink-4` 的取值是按「三种底色上最差不低于 4.5:1」
反算出来的，不是挑好看的）。

**窄屏不丢能力**：窗口宽时右栏与队列并排常驻；变窄后（≤1180px 收右栏、≤900px 收队列）它们**不是消失**，
而是变成**浮层抽屉**——图标轨上出现对应入口，唤出后浮在正文之上，**点遮罩、按 Esc、点右上角 ✕，
或再点一次入口**都能收回；窗口拉宽后自动归位。窄屏下点队列里的某一条，抽屉自己让位（选完就该看正文）。

**取消是真取消**：等待期间给的是「已跑多久 + 现在走到哪一步（来自真实事件）+ 取消」。
点取消会让这次跑批**停在下一个环节边界**——资金动作之前的检查点保证「还没发生的动作一定不会发生」，
而**已经发生的处置不回滚**，提示语就照这个措辞（不假装能撤回，也不假装什么都没发生）。
浏览器关页面同理：连接断开即触发取消。

### 数据源（电商接口 / MCP）

左轨第三格进「数据源」：**6 个连接器**──订单中台、售后工单、物流轨迹、商品规格（4 个 MCP）、表格导入（文件）、微信客户消息（入站）。

- **MCP 是真连的**：`desktop/server.mjs` 启动时拉起 `mcp/server.mjs` 子进程，走完 `initialize` → `tools/list`，界面上点「拉取数据」时调 `tools/call`，拿回来的行交给 `src/ingest.ts` 校验并合并。服务端顶部的绿标写着「MCP 服务端已联通 · N 个工具」，连接的服务器名与版本号一并显示。
- **未联通时如实降级**：MCP 起不来就退回读同一份数据文件（同一份数据、同一处校验），连接器卡片标成「本地文件通路」，不静默产假数据。单文件版 `demo.html` 没有子进程，则明确标注为本地通路。
- **表格导入**：顶部选数据表（订单 / 退款申请 / 商品规格 / 物流 / 工单），粘贴或选文件导入 CSV / TSV / JSON，按主键 upsert。**脏数据不吃默认值**：缺主键、数值非法一律拒绝并列出行号与原因（实测「拒绝 2 行 · 第 1 行：qty 不是数字：abc / 第 2 行：第 order_id 列（主键）为空」）。中文 Windows 下 Excel 导出的 GBK 编码 CSV 会被自动识别并按 GBK 解码。
- **导入即刻生效**：引擎每次运行都实时从同一份 store 取数（`store.orders.find(...)`），所以刚拉进来的订单/退款单可以直接用来处理新的客户咨询——不必重启服务。

### 微信接入

数据源页的「微信客户消息」卡片：

- 本地入站口 `POST /api/inbound`，报文 `{ text, from, channel, msg_id }`；**同一 `msg_id` 重复投递自动去重，不会跑第二遍**（微信侧重复推送是常态）。
- 消息进来即触发一次完整处置：进队列 → 六步链路 → 自主执行或停办转审批 → 生成可回写的客户回复。界面上与手贴原话走的是同一条链路，结果直接出现在处置队列里。
- **重新打开页面，队列与指标接着上一轮**（服务端版）：入站流水里带着处置结果的最近 8 条会在启动时回灌成会话（同 `msg_id` 幂等），所以刷新后不会看到「已处置 5 条、指标却是 0」这种自相矛盾的画面；更早的只留流水、不占内存。单文件版一切都在页内内存里（没有服务端可回灌），**刷新即重置**——这是它「双击即用、不留痕」的另一面。
- 页面内可粘贴一条消息试跑，右侧是入站流水（已处置 / 已转审批 / 已去重）。
- 接真实微信的步骤写在卡片里（微信侧配回调 URL / Token / EncodingAESKey → 服务端验签解密 → 取 `FromUserName` 与 `Content` → 调本入站口 → 回复按客服消息接口回写）。凭据只进本地 `.env`。


### 人工跟进（Agent 交不出来的那些）

Agent 不是万能的：**被合规复核拦下的、诉求没说清的、审批被驳回的**，它交不出来，必须有人接。以前这三种案子只会显示一句「已转交专人跟进」——人看着这句话没有任何地方可以动手。现在它们是**可操作的跟进台账**：

- **在哪些案子出现**：被拦截 / 需补充信息 / 审批未通过，或它自己标了「需人工跟进」。右栏多出一块「人工跟进」，结果卡横幅上有「去跟进」，队列条目带 `跟进中 / 待接手 / 已结单` 小标签。
- **「去跟进」从哪点都能落到这一条**：结果卡横幅、回复区提示、队列条目上的跟进标签、右栏概览的「接着跟进」——**四个入口共用同一个跳转函数**。点哪个案子就落到哪个案子的跟进面板，不会「跳去第一条待接手」。窄屏下点它，**右栏抽屉会自己唤出来**（不会对着看不见的面板空滚）。跳转后地址变成 `#fu/案件编号`，**刷新或把链接发给别人，都能直接落回这一条**。
- **能做什么**：① **接手跟进**（署名认领，这条归你）；② **记一条**（跟进记录，带时间与作者，按时间线累积）；③ **已联系客户，等补充**；④ **转交**（转给二线，跟进人随之改）；⑤ **核实完毕，结单**。
- **最要紧的是「按补充事实重新处置」**：把客户补到的事实写进跟进框，点一下 —— 它会**带着这条补充事实真的重跑一遍完整链路**（重新取证、重新复核、重新过授权闸），新结果作为一条新记录进队列，原案台账里留下一笔「按补充事实重新处置」。
  **要说清的边界**：补充事实能不能改变结论，取决于引擎是否采纳它。实测 M02（未收到货·物流已签收）补了「门卫代签、本人未取件」后**仍判拦截**——因为签收事实在物流记录里；人工跟进的终点往往是结单或转二线，这正是它存在的意义。**不是「人工写了就能过」**，写进去的只是事实，判断仍然归引擎和授权闸。
- **台账会连着案子和结果一起存**（服务端版）：重新打开页面时，跟进记录、它记的那条案子、以及**「按补充事实重新处置」跟出来的那条结果**一起回来，不会出现「台账还在、案子没了」或「记录还在、成果没了」的断头路。跟进人署名也记住，不用每次重填。
- **接口**：`GET /api/followups`（台账）、`POST /api/followup`（`{ case_key, action, by, note, target, case, run_case }`，`action ∈ claim | note | wait | reassign | rerun | close`）。

**人工审批卡（四问设计）**——按审批控制台的标准写清「为什么停下来 / 依据是什么 / 我能做什么 / 做完会怎样」：

```
待人工审批  仅退款   单号 20261015-01                    ¥1,299.00
该笔处置金额 ¥1299 超出 Agent 可自动处置上限 ¥500，按政策必须由人工审批后执行。
├─ 客户说了什么         客户原话
├─ Agent 的判断依据      可退上限 = 实付 + 服务费；金额口径一致；物流签收事实；客服工单已核验……
├─ 它拿不准的地方        签收人=代收点/门卫，责任归属没有确定口径（主动暴露考虑过但否决的备选）
├─ 批准 / 驳回分别会怎样  批准后执行退款并向客户发送到账通知，本次会话直接结单
│                        驳回后不执行退款，转为转交专人向客户说明并跟进
└─ [审批人] [驳回理由]   [批准并执行]  [驳回]
```

**批准 = 真实执行并结单，驳回 = 如实收口未执行**，两条路都不需要人再点第二次（续办时冻结本次参数、不重跑，避免金额漂移）。**驳回的案子会自动落进上方的人工跟进台账**——「已转交专人跟进」得有人真接手才算完。

**五档状态**：已自动处理 / 待人工审批 / 已拦截 / 审批未通过 / 需补充信息——数字由会话结果状态机实时推导，不是预置数字。

**两层术语防护，保证工程词零泄漏**：

1. **映射层**：内部枚举全部翻译成使用者语言——`PASS`→复核通过、`REJECT_FACT_CONFLICT`→未通过：信息与记录不符、`EXECUTE`→已自动处理、`APPROVE`→待人工审批、`full`→完整核查、`orders`→订单。
2. **`sanitize()` 渲染净化**：所有自由文本（判断依据、复核意见、审批理由、执行结果、给客户的回复）渲染前强制过一层替换——工具名 → 人话、枚举 → 中文、规则编号（AM-01 / SR-01）剥离。防线不依赖源头数据自觉。

该洁净度用**工程术语卫哨**验收：真实 Chromium 扫描 `.app` 渲染文本，**50 项禁止词**（`src/`、`.ts`、`cli`、`--`、`offline_rule`、`aftersales.`、`GOLD`、`退出码`、`JSONL`、`PASS`、`EXECUTE`、`APR-`……）零命中才算过——首屏 / 审批页 / 批准后 / 驳回后**四个视图全部 clean**。实测记录见 `运行证据-自主处置台改版-2026-10-15.txt`。

界面与命令行**共用同一份门禁判定**（`src/gate.ts` 从 `cli.ts` 抽出，UI 不另写一套裁判），所以处置台上显示的结果与 `--gate` 退出码是同一个口径。

**HTTP API**（脚本可调，前端就是调这套）：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/` | 处置台前端（单文件，内联 JS/CSS） |
| GET | `/api/bootstrap` | 样本集 + 工具注册表（`registry`）+ Node 版本 + 当前模式（是否检测到可用密钥） |
| POST | `/api/run` | 跑一个样本（传 `msgId`）或一句原话（传 `text`）；`deferApproval:false` 可让审批环节立即裁决（脚本用） |
| POST | `/api/run/stream` | **同一次跑批的流式版本**：NDJSON，先 `{"type":"start"}`，再逐条 `{"type":"event","line":…}`（引擎轨迹原样，不加工），末尾 `{"type":"result","result":…,"pending":…}`；客户端断开即取消（在环节边界停下，尚未发生的资金动作不执行）。与 `/api/run` 共用同一份编排与收尾逻辑，不会出现「一边记账一边不记」 |
| GET | `/api/approvals` | 当前待人工审批队列 |
| POST | `/api/approve` | 裁决一张审批单（`{id, approved, approver, note}`）；批准则真实执行并结单，驳回则按未执行收口；同一单不可重复裁决 |
| POST | `/api/gate` | 8 样本门禁，返回逐条期望比对与汇总 |
| GET | `/api/connectors` | 数据源清单：连接器声明 + 各表实时规模 + MCP 服务端联通状态与工具清单 |
| POST | `/api/connectors/pull` | 从连接器拉数并入引擎（`{id}`，`"*"` 为全部）；走 MCP `tools/call`，未联通则走本地文件 |
| POST | `/api/ingest` | 粘一段 CSV / TSV / JSON 直接入引擎（`{dataset, text}`），按主键 upsert 并返回新增 / 更新 / 拒绝明细 |
| POST | `/api/inbound` | 微信客户消息入站（`{text, from, channel, msg_id}`）→ 去重 → 自动处置 → 返回结论与可回写回复 |
| GET | `/api/inbound` | 入站消息流水（含去重命中记录） |
| GET | `/api/followups` | 人工跟进台账（谁在跟、跟到哪一步、每次做了什么） |
| POST | `/api/followup` | 记一笔人工跟进（`{case_key, action, by, note, target, case, run_case}`，`action ∈ claim\|note\|wait\|reassign\|rerun\|close`；`rerun` 前由前端重跑链路，`run_case` 即那次重跑的结果快照） |

**MCP 服务端**（可独立接入任意 MCP 宿主）：`mcp/server.mjs` 是零依赖 stdio MCP 服务端，按 `data/connectors.json` 的声明暴露 9 个工具（`commerce.orders_list`、`commerce.refunds_get`、`commerce.logistics_get`、`commerce.sku_list`……）。工具面不硬编码，接新平台改声明即可。用法见 `mcp/README.md`。

## 配置（模型模式）

**在界面上改**（推荐，改完即生效、不用重启）：桌面端左边图标轨最下面那个滑杆图标，或直接打开 `http://127.0.0.1:8787/#config`。四项配置、状态的诚实口径（填齐 ≠ 连得上）、一次真实的连通测试都在这一页。

**也可以改文件**：

```bash
cp .env.example .env   # 然后填入可用密钥
```

| 键 | 说明 |
|---|---|
| `LLM_BASE_URL` | OpenAI 兼容服务地址（默认智谱 `https://open.bigmodel.cn/api/paas/v4`） |
| `LLM_MODEL` | 模型名 |
| `LLM_API_KEY` | 密钥。检测到占位值（`在此填入` / `xxx` 等）会明示「不可用」 |
| `LLM_TIMEOUT` | 超时秒数，默认 60 |

界面配置页的三条边界（写在 `desktop/server.mjs` 的 `maskKey` / `writeEnvPatch` 与 `src/env.ts` 的 `resetEnvCache` 旁边）：**只回显密钥末 4 位**；**密钥框留空 = 保持原值**（要清空得单独勾，避免「没填就被清掉」）；**保存后重载配置缓存**（否则文件改了、进程里还是旧值，表现为「保存成功但不生效」）。写回时只改这四行，`.env` 里的注释与其余内容原样保留。

**失败不静默**：非 `--offline` 且密钥不可用 → 退出码 2 并说明原因，绝不假装成功。模型输出形状非法（`case_type` 越界 / `amount` 非数字 / 缺 `customer_text`）同样抛错，不吃默认值。

**两种模式都已实测**：`--gate --offline` 与 `--gate`（真实密钥）均 8/8 符合期望、退出码 0；M01 单样本在模型模式下 `judge_source = model`、轨迹 `judge_mode = model`。

**故意没装进去的（以及为什么）：**

| 排除项 | 原因 |
|---|---|
| **`.env`** | **含真实 API 密钥。这是打包时唯一不能妥协的一条**——包要发给别人，密钥不能跟着走。首次运行按 `.env.example` 自己填；不填就加 `--offline`，全链路照常跑通 |
| `runs/` | 运行产物（571 个决策轨迹 JSONL），每次跑案件自动重建。带上只会让包变成「别人上次的痕迹」 |
| `data/memory/` | 同类案检索索引的缓存，由 `runs/` 的轨迹回读生成。目录不存在时 `src/memory.ts` 会重建（`!existsSync(RUNS_DIR)` 直接返回 0，不报错）——**首次运行从空索引起跑是正常的** |
| `.tmp/` `.dash/` | 本地验证脚本与早期调试落盘，无代码引用，不属于交付内容 |
| `publish/` | 线上发布用的目录（`index.html` 是 `demo.html` 的旧副本）。发布是独立操作，且当前这份是旧版——**包里给的是最新 `demo.html`，不要拿 `publish/` 当参考** |
| `research/` | 2 张对标研究用的外部参考截图，属调研输入，非工程内容 |
| `node_modules/` | 根本不存在——零第三方依赖，没有这个目录 |

**拿到包之后，三步确认它活着：**

```bash
cd craft-aftersales-agent
node --version                          # 需要 ≥ 22.18；仅用 demo.html 则完全不需要
node src/cli.ts --gate --offline        # 退出码 0 = 8 个样本全部符合期望
```

只要门禁放行，就说明源码、数据、契约、判据四层都是齐的——这一条比「能打开界面」强得多，因为它逐条比对行为而不是只看有没有报错。

## 五分钟看懂它硬在哪（挑三条）

1. **取证环节结构上摸不到可执行工具**：`assemble(tools, "investigate")` 只返回 5 个只读查询，且编排层有断言——装配里出现可执行工具直接抛错。不是「提示词请勿执行」，是「拿不到」。
2. **摘掉 Reviewer，坏样本立刻放行**：`--ablation` 对 BAD 样本跑两遍——带 Reviewer 阻断 2/2；摘掉后 M07（申请退 500、实付 268）直接放行执行。门禁有效性有可执行的对照证据，不是口头声明。
3. **授权跟着金额走，不跟工具走**：同一把 `aftersales.decide_refund`，49.90 直接执行（EXECUTE）、389 先问人（ASK）、1299 挂起等审批（APPROVE，Agent 无权执行）。

## 已知边界（面试被问就照这个答）

- 数据全部合成，非真实业务数据。
- **模型链路已用真实密钥实测**：`--gate` 模型模式 8/8、退出码 0。但它是调了三轮提示词与数据契约才全绿的（判定优先级、SOP 触发词契约、`follow_up_required` 的确定性归属），说明模型版对提示词与领域契约敏感——**换领域要重跑门禁，不能照搬「已验证」这个结论**。
- SOP 另定义 `RETURN_REFUND` / `COMPLAINT` 两类案件，8 条样本未覆盖（`RETURN_REFUND` 的「退货运单+退款」双动作序列需要把审批环节扩展为多动作，当前实现演示单动作）。
- 情绪识别与意图归一的**离线版**是关键词规则版；模型版同构且已验证，但只在这 8 个样本上验证过，泛化能力未测。
- **连接器返回的是合成快照数据**（`mcp/data/*.csv`），不对应任何真实商家。接真实平台要走商家开放平台授权（AppKey + Secret 换 access_token），凭据只进本地 `.env`；`mcp/server.mjs` 里把 `readRows()` 换成真实 API 调用即可，别的不用动。
- **微信入站是本地口**：`POST /api/inbound` 已具备去重、触发处置、可回写回复的完整行为；真实接收需要在微信侧配置回调地址与 Token/EncodingAESKey 并转发报文（步骤写在数据源页卡片里），本工程不含微信侧的验签解密实现。
- **模型模式一条案件约 20–30 秒**（多轮提示词 + 真实网络），规则模式毫秒级。演示时点顶栏引擎标识可随时切换，两者处置口径由同一套 SOP 与授权闸决定。
- **接口设置页只在服务端形态可用**：它要写回项目根 `.env`，所以需要一个进程。单文件版没有进程，这一页如实说明原因并给出本地服务模式的启动命令，**不摆一组填了也存不下去的输入框**。另外「填齐」不等于「连得上」——界面分三档（未就绪 / 已填齐 / 连通已验证），只有真跑过一次补全才算验证过。
- **「同类案子过去怎么处理的」只在服务端形态出现**：它读的是 `runs/*.jsonl` 里已经落盘的决策轨迹（449 个会话 → 447 张案件卡）。单文件版跑在浏览器里，虚拟文件系统没有目录枚举能力、也没有历史轨迹，所以那一块**不出现**——不做假数据。判定完全不依赖它：召回结果只拼进提示词当参考，**授权金额档位只认订单账本**。
- **台账在服务端形态下跨重启保留，单文件版刷新即重置**：人工跟进记录与审批单落在 `data/ledger/*.jsonl`（append-only 事件流 + 启动回放），重启后跟进台账原样回来。但**续办句柄是闭包、跨不了进程**，所以重启后还挂在队列里的审批单会标成「已失效 · 待重新处置」，给的是「重新处置这条」（按原话重跑一遍），而不是一个点了会报错的「批准执行」。
- **处置失败的那条会留在队列里，状态是「未跑通」**：不删记录、不假装还在跑，而是就地给出失败原因、下一步做什么，以及一个「原样重试」（点它会顶掉原记录，不是再挂一条）。这条口径是刻意的：失败时唯一还值得看的就是「刚才跑的是什么、为什么没成、能不能再试一次」。
- **MCP 通道状态是探测出来的，不通就当场说**：连接器拉数走 MCP 协议（`mcp/server.mjs` 子进程）。子进程退出 / 握手超时 / 写入管道断掉，都会立刻把通道标成不可用并让在飞的请求立刻失败（**不会**出现「子进程已死、界面还显示已联通」）。不通时拉取会自动改走本地文件通路，读的是同一份 CSV、走同一处校验，并且**如实标注 `via=file` 并把原因带回界面**。数据源页的「数据通道」面板逐条给出：连接方式 / 服务端 / 工具前缀 / 在线工具 / 握手耗时 / 单次调用上限 / 尝试连接，并配一个「重连」。超时时间可用 `MCP_TIMEOUT`（单次调用，默认 10 秒）与 `MCP_HANDSHAKE_TIMEOUT`（握手，默认 8 秒）调整。单文件版没有进程可拉，所以那一页写「本形态无进程，走文件通路」且**不摆重连按钮**。
- **连接器声明里的 `get` 类工具目前没有调用点**：`orders_get` / `refunds_get` / `logistics_get` / `sku_get` 只在 `tools/list` 里被列出，界面与引擎都只做整表拉取（`list` 类）。这不是缺陷（拉取不依赖它们），但是一条「声明了却没接上」的缺口，接单条查询时才需要补。
