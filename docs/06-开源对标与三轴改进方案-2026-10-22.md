## 一、先说检索结论：这个赛道"业务同构"的开源项目，几乎没有成品

按"电商客服 / 退换货 / 退款"检索到的仓库，能真正跑通处置链路的都很小：

| 仓库 | 星 | 语言 | 它做了什么 | 能不能当对标对象 |
|---|---|---|---|---|
| `gohft/Agentic-RAG-Customer-Support` | 0 | Python | LangGraph + RAG 答退换货政策，其余升级人工 | 只能当**思路**参考 |
| `iaan-khan/ai-cs-agent-langgraph-` | 0 | Python | 鞋类电商，动态调工具校验政策、查客户、批/拒退款 | 同上 |
| `Kirannpatil/Ecom-agent` | 0 | Python | 多工具客服：物流、商品、退换货资格、FAQ + 护栏 + 评估 | 同上 |
| `amitisoft/mcp-agent-demo-Abhinay` | 0 | TypeScript | MCP 版客服，超政策限制则阻断或升级 | 唯一 TS 同栈，但仍是骨架 |
| `nexscope-ai/eCommerce-Skills` | 1,226 | Python | 电商**技能集**（选品/营销/供应链），不是处置 Agent | 参考"技能怎么拆" |
| `Shopify/claude-for-commerce-examples` | 145 | Python | Anthropic commerce blueprint 的 Shopify 实现（导购 + 商家侧） | 参考"官方怎么划边界" |

**这条结论本身值得写进汇报口径**：售后处置这个方向，开源侧普遍停在"能对话 + 能调工具"，很少有人把**授权闸、只读复核、门禁回归**做成可审计的一等公民。本项目的差异化不在"更像人"，而在"每一步都能被追问为什么"。

所以下面的对标不做"整包替换"，而做**机制拆借**：从前端、记忆、runtime 三个方向各取最强的几家，只抄它的**分层与口径**，不引入它的运行时。

## 二、三轴对标：谁是这一轴的"事实标准"

### 2.1 前端交互

| 仓库 | 星 | 核心结构 | 我们能借什么 |
|---|---|---|---|
| `CopilotKit/CopilotKit` | 38,176 | "Frontend Stack for Agents & Generative UI"，自建 AG-UI 协议，React/Angular/Mobile 多端 | **生成式 UI 的协议层思路**：把"工具调用/审批"当作可渲染的一等消息类型，而不是事后拼字符串 |
| `assistant-ui/assistant-ui` | 12,672 | 可组合 primitives：`Thread` / `Message` / `Composer` / `ThreadList` / `ActionBar`；`runtime` 适配器（AI SDK / LangGraph / AG-UI / A2A / 自定义 data-stream）；生成式 UI 支持**内联人审** | **组件分层方式**："primitive 管结构、runtime 管数据、主题管像素"，以及把审批做成消息块而不是弹窗 |

关键一点：assistant-ui 明确把"内联人工批准（inline human approvals）"列为生成式 UI 的能力，而不是单独一个审批页。这正好对上本项目上一轮踩过的坑——**「状态词 + 一个按钮」不算闭环**，审批与跟进必须能被"就地处理"。

## 三、候选筛选：按"能落到这个仓库"重新打分

打分维度（每项 1–5，5 = 最匹配）。**"可抄机制"与"可直接依赖"分开打**，因为这个项目有两条硬约束：**零运行时依赖**、**单文件版必须能双击打开**。

| 候选 | 技术栈匹配 | 机制可抄 | 接入成本（越高越差） | 与单文件版冲突 | 综合 | 结论 |
|---|---|---|---|---|---|---|
| assistant-ui | 2（React + 打包链） | 5 | 高 | **强冲突** | 7/20 | 抄分层，不引入 |
| CopilotKit | 2 | 4 | 高 | 强冲突 | 6/20 | 只借"生成式 UI 是协议"这个判断 |
| mem0 | 1（Python + 向量库） | 5 | 高 | 强冲突 | 6/20 | 抄算法口径（ADD-only + 多信号） |
| letta | 1 | 4 | 高 | 强冲突 | 5/20 | 借"常驻块 / 归档层"两级 |
| genome | 2 | 3 | 中 | 冲突 | 5/20 | 借 bi-temporal 概念 |
| langgraph | 1（Python；有 JS 版 3.4k） | 3 | 中高 | 中（JS 版需要依赖） | 6/20 | 借"人审即检查点"，不引图引擎 |
| temporal | 1（Go 服务） | 3 | **很高**（要跑服务） | 强冲突 | 4/20 | **不采纳**，只借重试边界 |
| cordum | 1（Go） | 3 | 高 | 冲突 | 5/20 | 对照"审批证据"，不改代码 |
| workflowbuilder | 2 | 3 | 高 | 强冲突 | 5/20 | 借运行可视化的产品形态 |

**结论一句话**：这个项目不该"引入框架"，而该"引入机制"。理由不是懒——是它的两条硬约束（零依赖、单文件可发布）恰好挡住了所有热门框架；而它已经有的东西（确定性六环节 + 授权闸 + 只读复核 + 门禁 8/8）比任何候选都更接近"可交付"。

## 四、现状体检：三个方向各自的真实问题（带位置）

### 4.1 前端

规模：`desktop/public/index.html` 单文件 2,690 行（HTML + CSS + 全部 JS），无框架、无构建。

| 问题 | 位置 | 后果 |
|---|---|---|
| **全量重渲染** | `renderAll()` 一次性重建 metrics / queue / stage / side 四块 | 任何状态变化都重建整屏：输入焦点丢、滚动位置丢、抽屉动画重放 |
| 渲染即字符串拼接 | `renderQueue` / `stageHtml` / `renderSide` 各自拼 HTML | 无法局部更新；无法对渲染做单测；XSS 全靠 `esc`/`sanitize` 的手工纪律 |
| 事件靠选择器 | document 级委托 + `near("[data-xxx]")` 分支链 | 同一个词两套语义（"去跟进"前科）；加动作只能往 if 链里塞 |
| 三态不统一 | 各视图各写 loading / empty / error | 慢通道等待时四块各自闪，观感不一致 |
| 表单被重渲染打断 | 本轮实测：保存配置时不能 `renderAll()`，只能手动改按钮 | 这是"补丁感"的来源，不是设计 |

### 4.2 记忆

| 问题 | 位置 | 后果 |
|---|---|---|
| **轨迹只写不读** | `src/trace.ts` 全类方法只有 `append` / `all`；`runs/` 下已有 **429 个文件 / 6,644 行**，`src/` 里没有任何回读 | 6,644 行历史对决策零贡献，是纯"事后取证" |
| 台账在内存 | `desktop/server.mjs:135` `pendingApprovals = new Map()`；`:141` 注释自认"重启即清空" | 重启丢审批单与跟进状态 |
| 会话内记忆只有一次 run | `src/tools.ts:63` `RunContext` | 跨案件、跨客户无累积 |
| 无检索层 | 全工程 `grep` 无 `embed|vector|retriev|rag` | "同族案子过去怎么处理的"问不出来 |
| 上下文无预算 | `src/context.ts:31` `buildContext` 有**三层披露**，但没有 token 上限与裁剪策略 | 证据一多就顶到模型上限，靠运气 |

### 4.3 Runtime

| 问题 | 位置 | 后果 |
|---|---|---|
| 请求无排队 | `desktop/server.mjs:232` `createServer(async (req,res))` 直接跑，无并发上限 | 模型模式一条 20–30 秒，两个人同时点就互相拖慢 |
| 补证轮次硬编码 | `src/agent.ts:234` 的 `if (rv.missing_evidence.length)` 只跑一轮 | 要么"补一次就够"要么"永远补不齐"，没有预算概念 |
| 无重试 / 无退避 | `src/llm.ts` 只有 `AbortController` 超时 | 429 / 5xx 一次就整体失败 |
| 轨迹同步写盘 | `src/trace.ts` `append` 每行 `writeFileSync` | 每步一次同步 IO，正好在关键路径上 |
| 取消不传播 | 前端"取消等待"只中止前端 | 服务端照常跑完（已如实告知，但没得选） |
| 无可观测性 | 无环节耗时分解 | 说"变快了"没有证据 |

## 五、改进方案

排序原则用的是**能不能落地 + 能不能在面试里讲清**两条并重：先做"有现成坏样本能对照"的，再做"要加新概念"的。

### 5.1 前端交互与组件结构

**P0-a 渲染分片（脏标记）**
把 `renderAll()` 拆成四个独立单元：`renderMetrics` / `renderQueue` / `renderStage` / `renderSide`，配一个脏标记表；状态变更只标脏对应单元，末尾 `flush()` 一次只重绘变脏的那块。

- 做法：`const dirty = new Set()`；`markDirty("queue")`；`flush()` 遍历脏集调对应渲染函数并清空。
- 预期效果（可断言）：保存配置时 `document.activeElement` 保持不动；`stage.scrollTop` 不重置；单次交互的重绘单元数从 4 降到 1（加计数器 `window.__renderCount` 当验收断言）。
- 风险：脏标记漏标 → 界面不更新。缓解：开发期加"每次 flush 记录脏集"，验收脚本覆盖 8 条场景的每个交互。

**P0-b 动作表（action registry）替代选择器分支**
把 `data-*` 内联语义收敛成一张表：`actName → handler`，元素上只写 `data-act="gotoFollowUp"` 加参数属性，事件分派查表。这是把上一轮"入口各自实现必分叉"的教训**机制化**，而不是靠记性。

- 预期效果：新增一个可点动作 = 表里加一行 + 元素加一个属性；`near()` 分支链从 ~20 条 if 降到 3 条（滚动区/表单区/动作表）。

**P1-a 三态组件化**
抽 `viewState(state, {loading, empty, error})` 单一入口，四块视图统一走它。

- 预期效果：慢通道等待时四块共用同一套骨架与文案口径，不再出现"有的地方写'读取中'、有的写'请稍候'"。

**P1-b 组件化的两条路（先选 A）**
- **A（推荐，守约束）**：继续零依赖，但把"模板函数 → 按 key 复用节点"这层补上（自己实现约 30 行的 keyed patch），让局部更新成为默认。单文件版不受影响。
- **B（只在转产品时）**：换 Preact + 抄 assistant-ui 的 `Thread / Message / Composer` 分层与"审批作为消息块"的表达，再接 AG-UI 式事件流。代价：打包链、单文件版要重做。

**P2-a 无障碍补一层**
上一轮明确留白。这轮补：`focus-visible` 可见焦点、`aria-live` 播报处置结果、抽屉的 `aria-modal` 与焦点陷阱、Tab 路径。理由：审批类界面**键盘可用**是真实需求，不是装点。

**P2-b 生成式 UI 雏形**
把"六步执行流"从静态渲染改成事件驱动块（`phase / tool_call / approval / result` 四种块类型），后面接真实流式事件时渲染层不用改。借的是 assistant-ui / CopilotKit 的判断，不是它们的代码。

### 5.2 记忆机制：上下文存储、检索、长期管理

**P0-a 轨迹回读 + 案件索引（最小闭环）**
新增 `src/memory.ts`：扫 `runs/*.jsonl` → 每个会话抽一张"案件卡"（案件类型、处置结论、驳回码、金额区间、是否补证、是否翻案、人工补充事实、最终动作）→ 按案件主键 **upsert** 到 `data/case_index.json`。

- 检索：**先规则过滤（同族案件类型 + 金额±30% + 同驳回码）再 BM25**，不引向量库。理由三条：数据量只有几百条；零依赖是硬约束；**可解释**——能说清"为什么召回了这条"，这在售后场景比"相似度高"更重要。
- 用途：判据归纳时作**参考提示**（`advisory: true`），右栏给"同类案子过去怎么处理的（N 条）"。
- 验收：输入一条与 M07 同族的诉求 → 召回 ≥3 条；`--gate --offline` 仍 8/8（证明参考不改变判定口径）。

**P0-b 台账落盘（消灭"重启即清空"）**
`followups` / `pendingApprovals` 从内存 Map 改为 append-only JSONL + 启动回放（保留既有"业务主键 upsert、最新在前"的口径）。

- 验收：重启前后 `/api/followups` 条数一致；在等审批的单子重启后状态明确（继续等 / 标记失效），不留悬空。

**P1-a 上下文预算与裁剪可审计**
`buildContext` 加预算：取证 40% / 判据 25% / 回执 15% / 记忆参考 10% / 余量 10%；超预算按"证据重要性 × 新鲜度"裁剪，**裁剪记录进 trace**。

- 验收：模型模式单案件 prompt token 下降并记录（不写死具体百分比，跑出来是多少写多少）；gate 8/8 不变；trace 里能看到"裁掉了哪几条"。

**P1-b 长期记忆：客户画像（只增不覆写）**
按客户标识聚合 `data/memory/customer_<id>.json`：历史诉求、已赔付累计、争议记录、偏好。写入走 mem0 现行的"单遍抽取 + 只增不改"，冲突时**保留双方并标'有冲突'**（bi-temporal：分别记"何时为真"与"何时写入"），不静默取一个。

- **红线（必须写死在代码里）**：记忆只作参考，**不作授权依据**。`auth.ts` 的金额分档只读订单账本，绝不从记忆读金额——否则"记忆"就成了绕过审批的后门。验收要有一条负向用例：故意在记忆里写一条"该客户可全额退款"，验证审批档位不变。

**P2 记忆衰减与主动遗忘**
按"最近命中时间 + 业务重要性"做加权衰减；对超过保留期的流水做归档（移到 `data/archive/`），索引只留摘要。避免 6,644 行变成 66,000 行后索引本身成为负担。

### 5.3 Runtime：执行流程、调度与性能

**P0-a 执行预算与护栏**
`runCase` 加 `budget`：最大模型调用次数、最大工具调用次数、总超时。超限返回"未完成 + 原因"，**不假装完成**。补证回路从"1 轮硬编码"改成"最多 N 轮或预算耗尽即停"。

- 验收：构造一个必然触发补证循环的坏样本，验证在第 N 轮停下并给出原因；gate 8/8 不变。

**P0-b 轨迹异步写 + 退出 flush**
`Trace.append` 改内存缓冲 + 阈值/定时 flush，`process.on("exit")` 同步兜底。

- 验收：单案件写盘次数从 O(步数) 降到 O(1)/秒；用 `hrtime` 量 append 平均耗时，改进前后都记进证据。

**P1-a 请求层：排队 + 并发上限 + 幂等 + 有边界的重试**
`/api/run` 进内存队列（并发 2–3）；按 `msg_id` 幂等；模型调用指数退避，**只对 429/5xx/网络错误重试，4xx 不重试**。

- **安全红线**：重试与不可逆动作隔离——资金动作一旦执行，**不重试、不重放**，只重放"读"与"算"。这条是 Temporal 那套"活动可重试"搬到这里的必要变形。

**P1-b 取消传播**
前端取消 → `AbortSignal` 透传到 `callModel`；服务端把"已取消"如实写进 trace。与既有纪律一致：**不假装能撤回已经发生的处置**。

**P2-a 检查点续跑（借 LangGraph"人审即检查点"）**
每环节结束把 case state 落 `data/checkpoints/<case>.json`；进程重启可从最后一个完成的环节续跑。审批等待本身天然是检查点（`resume` 回调已存在）。

**P2-b 可观测性**
`--profile` 输出每环节耗时分解（理解 / 取证 / 判据 / 复核 / 审批 / 回执，且区分"模型等待"与"本地计算"），作为所有性能声称的唯一证据来源。

## 七、明确不采纳的候选，与理由

| 候选 | 不采纳的理由 |
|---|---|
| 整体换 LangGraph | 六环节是**确定性编排**，图的价值在动态路由与多 agent 分支；换过去要引入依赖、丢掉单文件版，收益不成正比。只借"人审即检查点" |
| 依赖 mem0 / letta | Python 服务 + 向量库，与"零依赖 + 双击即用"直接冲突。**抄算法口径**（ADD-only、多信号检索、常驻块/归档层）比接服务更有价值 |
| 依赖 assistant-ui / CopilotKit | React + 打包链，单文件版要重做。抄它的**分层**（primitive / runtime / 主题）与"审批是消息块" |
| 引入 Temporal | 要跑一个 Go 服务，运维成本远超本项目收益。只在"重试边界"这一条上借它的思想 |
| 拆成 multi-agent | 当前单 agent + 确定性环节 + 授权闸已经能给出可审计结论。拆多 agent 只会扩大不确定性面，且与"每一步可追问"的目标相反 |
| 追"更像人"的对话体验 | 售后场景的价值在"结论对不对、谁批的、凭什么"，不在语气。这四个 0 星仓库恰好证明：只做对话的，没人用 |

## 八、这套方案自己怎么被验收

三条底线，任何一条破掉就不算改好：

1. **门禁不动**：`--gate --offline` 与模型模式都必须保持 8/8、退出码 0。任何让判定口径漂移的"改进"直接回退。
2. **两条形态同步**：服务端版与单文件版各验一遍（历史前科：单文件版判重哈希掺了递增序号，永不判重）。每批改动都要重建 `demo.html` 并复核术语卫哨。
3. **声称必须有证据**：性能类结论一律来自 `--profile` 与实测日志，不写"应该会更快"；记忆类结论必须带**负向用例**（记忆不改变审批档位、参考不改变判定），只有正向召回不算数。

## 九、如果只做三件事（面试口径）

按投入产出比，只挑三件：

1. **把 6,644 行轨迹读回来做案件索引** —— 它把"事后取证"变成"经验复用"，且完全不改判定口径，风险最低、讲起来最清楚（"我的记忆不是向量库，是可解释的同族召回"）。
2. **渲染分片 + 动作表** —— 前者解决"一操作整屏重建"的手感问题，后者把"入口必分叉"的教训变成机制。两件加起来两天，但界面质感是别人第一眼唯一能评估的东西。
3. **执行预算 + 有边界的重试** —— 这是"能不能上生产"的分水岭：预算回答"它会不会失控"，重试边界回答"它会不会重复退款"。后者是这类系统最致命的失败模式。

## 十、证据附录：本方案里"现状问题"的实测数据

写方案最怕的是"听起来有理、其实是断言"。以下三条是当场量的，量法一并写明，方便复核或推翻。

### 10.1 轨迹规模（已落盘、无人读取）

- `runs/` 下 **429 个 JSONL 文件，合计 2.53 MB**，共 6,644 行。
- 单案件轨迹：最近运行在 **17–20 行**（M07 17 行 / M01 20 行 / M08 6 行）。
- 回读证据：`src/` 内对 `RUNS_DIR` 的引用只有 `trace.ts` 的**写入**（`mkdirSync` / `writeFileSync`），无任何 `readFileSync`。

### 10.2 `Trace.append` 逐行同步写盘的成本

量法：按 `trace.ts` 当前写法（`writeFileSync(..., { flag: "a" })`）循环追加 N 行，`process.hrtime.bigint()` 计时，本机 Windows。

| 轮次 | N | 总耗时 | 平均 |
|---|---|---|---|
| 1 | 200 | 2,692.6 ms | 13.463 ms/行 |
| 2 | 40 | 295.2 ms | 7.380 ms/行 |
| 3 | 40 | 85.6 ms | 2.141 ms/行 |
| 4 | 200 | 1,719.9 ms | 8.600 ms/行 |
| 5 | 200 | 1,581.1 ms | 7.906 ms/行 |

对照：同样 200 行**先在内存拼好、一次写入** = **1.0 ms（0.005 ms/行）**。

读数——**必须带上下文，否则会得出错误结论**：

- 波动很大（2.1–13.5 ms/行），这是 Windows + 杀毒软件实时扫描的典型表现，不是 Node 的问题。
- 换算到单案件（17–20 行）：**约 34–260 ms 的纯写盘开销**。
- 模型模式下这条成本被 20–30 秒的模型等待完全淹没，**改它不会让模型模式变快**。
- 但规则模式声称"毫秒级出结果"，同为几十毫秒量级 —— 所以写盘**有可能**占了规则模式总耗时的相当一部分。这是一条**待验证的假设**，验证方式就是 5.3 的 P2-b（`--profile`），不是结论。

### 10.3 前端"全量重渲染"的规模

- `desktop/public/index.html` 单文件 **2,690 行**（HTML + CSS + 全部 JS）。
- `renderAll()` 每次调用重建 metrics / queue / stage / side 四块，渲染方式为字符串拼接后整块赋值 `innerHTML`。
- 本轮的直接观察（不是推断）：配置页保存时**不能调用 `renderAll()`**，只能手动改按钮文字与禁用态 —— 因为重建会把用户刚输入的密钥框、焦点、测试结果一并冲掉。这是"全量重渲染"最直观的代价，也已写进那一轮的代码注释。

## 十一、这套方案的风险与自我限制

| 风险 | 表现 | 缓解 |
|---|---|---|
| 记忆召回污染判定 | 相似案件被当成依据，导致"同案不同判" | 记忆结果强制带 `advisory: true`，`auth.ts` 不从记忆读金额；验收含负向用例 |
| 渲染分片漏标脏 | 某块界面不更新，且**不报错** | 加渲染计数器与脏集日志；验收覆盖 8 条场景的每个交互 |
| 预算设得过紧 | 正常案件被判"未完成" | 预算先按现有最大案件的 2 倍取值，跑满 8 样本 + 消融后再收紧 |
| 幂等键设计错 | 重复入站被当成新案件，或被误判为重复 | 沿用既有 `msg_id` 去重口径，不新造键；幂等只加在"写"而不加在"读" |
| 队列掩盖慢 | 排队后前端只看到"转圈更久" | 队列位置与预计等待必须回给前端（不编进度，只给"前面还有 N 条"） |
