# 01 · 需求拆解

> 任务书要求：「严格按照简历要点，设计并实现一款可运行的售后 agent demo……覆盖用户咨询理解、售后问题分类、工单或业务单据处理、结果反馈等关键链路」。
> 本文先把需求拆成可验证的条目，再说明每条链路由哪些文件、哪些运行证据支撑。

## 一、项目定位（一句话）

**客户已经决定要退单 / 换货 / 催件之后，售后工作员在后台做的处置工作，交给一个 Agent 从「客户的一句自然语言」开始端到端完成。**

与「退款核对工具」的分界线在**入口**：本项目的输入是 `我8月8号买的那把椅子，颜色跟图片差太多了，我要退钱。` 这样一句话，不是系统里的退款单号。订单要自己从文本里解析，退款单有可能根本不存在（系统里还没建），工单要不要新建由 Agent 自己判定。

## 二、需求拆解表

| # | 需求 | 验收标准（可跑） | 实现位置 |
|---|---|---|---|
| N1 | **用户咨询理解**：自然语言 → 结构化意图（诉求类型 / 订单线索 / 情绪 / 槽位） | `--ask "我8月12号买的那把椅子……给我换一件"` 能解析出订单号与目标规格；解析不出时不猜，转追问 | `src/understand.ts`（`resolveOrder` 日期+商品词打分、`detectCaseType`、`detectSentiment`） |
| N2 | **售后问题分类**：意图 → SOP 案件类型 → 走哪条路径 / 取哪些证据 / 要不要新建工单 | 8 条咨询分别归一为 4 种案件类型；换货案（系统无退款单）能判定「需新建工单」 | `src/classify.ts` + `data/sop.json` 六种 `case_types` 定义 |
| N3 | **工单 / 业务单据处理**：跨五源取证、补证回路、判责归纳、单据创建 | full 路径样本全部发生「首轮保守取证 → Reviewer 驳回补证 → 补证后重判」；换货工单 / 退款处置真的被执行并留痕 | `src/tools.ts`（工具面）、`src/agent.ts`（取证与补证回路）、`src/judge.ts`（判据归纳） |
| N4 | **结果反馈**：内部结论 → 客户可读回执 + 内部结单说明，不做过授权承诺 | 被阻断的案件回执是「转人工跟进」而非「已处理」；未获授权的退款不写成已退 | `src/reply.ts`（双轨回执 + 分支优先级） |
| N5 | **全链路可回放**：每一步决策落盘，可按行回放、按步定位 | `runs/*.jsonl` 首行会话头 + 每行一事件；工具调用带 `args_hash` 与 `fields_snapshot` | `src/trace.ts` |
| N6 | **端到端可跑通且可回归**：行为被样本集锁定，改动破坏行为立即失败 | `--gate` 8 样本全绿（退出码 0）；两个负向实验证明门禁有效 | `samples/cases.json` + `src/cli.ts` |

## 三、链路与简历四要点的映射

简历上这个项目写了四个能力点，本工程对每个点都给了**可指到文件的实现**，而不是只给名词：

| 简历要点 | 本项目落点 | 验证方式 |
|---|---|---|
| **① 取证与工具面**：统一命名空间、按环节动态装配、三层渐进式上下文披露 | `data/tool-registry.json`（8 工具全声明 `aftersales.*` 全限定名、各自声明允许出现的环节）；`src/tools.ts assemble()`；`src/context.ts`（摘要层 / Schema 层 / 字段级契约按环节展开） | 轨迹 `investigate plan` 行显示「装配 5 个只读工具」；`judge plan` 行显示三层披露展开率；取证环节装配里无可执行工具由断言保证 |
| **② 授权策略下沉为强制校验**：三档授权 + 按金额动态升级 + 审批回调回路 | `src/auth.ts`（只读 AUTO / 非资金不可逆 ASK / 资金类 ≤100 EXECUTE、≤500 ASK、>500 APPROVE）；`requestApproval()` 交回宿主裁决并回写 `approver/decision/at` 三项留痕 | 样本 S01/S06 走 ASK（确认后执行）、S04 走 EXECUTE（直接执行）、S03 走 APPROVE（挂起，Agent 无权执行） |
| **③ 上下文工程**：不全量灌入，按环节只展开相关层 | `src/context.ts` + `src/prompt.ts`（四段式提示词：角色与边界 / 可用证据与时机 / 输出格式 / 失败与兜底） | 判责环节的提示词只带本案相关字段契约；`--json` 输出可见每层 `disclosed` 状态 |
| **④ 只读 Reviewer 独立核验 + 决策轨迹 JSONL + 回归门禁** | `src/reviewer.ts`（无工具句柄，结构上不可能执行操作；只有驳回权与补查请求权，补查计划受「只能含 `aftersales.query_*`」护栏约束）；`src/trace.ts`；三级样本集 | `--ablation`：摘掉 Reviewer 后 BAD 样本阻断率 2/2 → 0/2；`--violation-demo`：绕过 clarify 保护被 SR-01 硬阻断 |

## 四、四链路的数据流（端到端）

```
客户一句话（data/messages.json，或 --ask 临时输入）
   │
   ▼ 链路一 · 理解（understand.ts）
Intent{case_type, order_id, sentiment, needs_escalation, slots}
   │
   ▼ 链路二 · 分类（classify.ts + data/sop.json）
Classification{sop_path, required_sources, money_action, needs_new_ticket}
   │
   ├─ sop_path = clarify ──────────────────────────────┐
   │                                                    ▼
   │                                        只追问，不进取证与判责
   │                                        （Reviewer 确认并给 CLARIFY_NEEDED）
   ▼
 链路三 · 单据处理（agent.ts 编排）
   investigate：按环节装配只读工具 → 首轮保守集取证
   judge：三层上下文披露 → 判据归纳（judge.ts / 模型）
   review：只读 Reviewer 复核 ──缺证据──▶ 补证一轮 → 重判 → 再审
   approve：授权分档 → 审批回调 → 执行 or 挂起
   │
   ▼ 链路四 · 反馈（reply.ts）
Reply{customer_text, internal_note, follow_up_required} + 全程 JSONL 轨迹
```

## 五、非功能需求（同样可验证）

| 需求 | 落实 |
|---|---|
| 模型不可用时不静默降级 | 非 `--offline` 且密钥不可用 → 退出码 2 并说明原因；`--offline` 明走规则占位，`judge_source=offline_rule` 全程标注，绝不冒充模型判断 |
| 模型输出不吃默认值 | `understandWithModel` / `normalize` / `replyWithModel` 全部校验形状，非法即抛 `ModelError` |
| 新增数据源不改编排 | 工具注册表声明式：加一条声明 + 一个 runner，装配 / 授权 / 上下文自动继承 |
| 零第三方依赖 | 仅 Node ≥22.18 原生 TypeScript 类型擦除，无 `npm install` |
