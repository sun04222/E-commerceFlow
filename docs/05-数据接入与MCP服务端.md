# 05 · 数据接入与 MCP 服务端（2026-10-15）

本文件记录三件事：**对标了什么**（GitHub 与市面上的电商 Agent 怎么接数据）、**据此定了什么**（连接器声明式设计 + MCP 服务端 + 导入校验口径）、**落地与实测结果**。

---

## 一、对标：数据接入这件事，别人怎么做

| 项目 | 定位 | 数据接入方式 | 对本项目的可用结论 |
|---|---|---|---|
| Shopify `claude-for-commerce-examples` | 官方参考实现 | 三层：**UCP**（业务能力协议）→ **MCP**（工具暴露）→ **Claude blueprint**（编排）。商家 agent 的写操作强制人工批准 | ①「取数」与「编排」要分层，编排层不直接认识平台；②写操作要留人工闸——本项目已有三档授权闸，且在它之上补了**预置审批看板**（官方样例没有） |
| Anthropic `commerce-agents` blueprint | 参考架构 | 工具面按业务能力切，工具名带命名空间 | 与本项目 `aftersales.*` / `commerce.*` 命名空间化的做法同向 |
| `TonyWang-hub/mcp-cn-commerce` | 中国电商 MCP 集合 | 抖店 / 淘宝 / 京东 / 快手 / 小红书 / **微信小店** 各一个只读连接器，stdio 配置格式 | ①国内平台形态就是「一家一个连接器」；②连接器应是**只读取数**，写动作留在编排层；③stdio 是事实标准，本项目随之 |
| `vinsblack/commerce-ai-agent` | React 管理台 + 集成页 | 独立 integrations 页面管理 MCP 适配器，连接器有「已连 / 未连」状态 | 数据源要**有独立页面**、要显示连接状态与实际数据量 |
| `lokeshrangineni/ai-e2e-project`（ShopChat） | MCP server 子进程 + 角色化工具可见性 | MCP 服务端作为**子进程**被宿主管辖 | 宿主进程拉起 MCP 子进程、按协议握手，是可行且常见的形态 |
| `nitin27may/e-commerce-agents` | Next.js 管理台 | 交互卡片式界面 | 界面要能**点得动**，不能只读展示 |
| `didilili/shopkeeper-agent` | 流式过程可视化 | — | 已在上一版（六步执行流）吸收 |

**市面产品的共同点**（也解释了用户为什么不满意上一版）：

1. 数据接入都是**独立一页**，不是散落在各处的「导入按钮」；
2. 接入后**立刻能看到规模**（多少订单、多少退款单），而不是等用的时候才发现没数据；
3. 成熟产品**不解释自己**——首页是工作台或对话，不是「我能做什么」的三张卡。

## 二、据此确定的设计

### 1. 连接器 = 一份声明，不是一个类

`data/connectors.json` 声明 6 个连接器，每个连接器声明它的平台、数据表、工具、以及数据文件：

```json
{
  "id": "orders-hub", "kind": "mcp", "badge": "MCP",
  "platforms": ["抖音小店", "微信小店", "天猫", "拼多多", "快手小店"],
  "tools": [
    { "name": "orders_list", "op": "list", "dataset": "orders", "file": "mcp/data/orders.csv" },
    { "name": "orders_get",  "op": "get",  "dataset": "orders", "file": "mcp/data/orders.csv", "key": "order_id" }
  ]
}
```

三种取数形态共用一套收口：

| kind | 含义 | 取数方式 |
|---|---|---|
| `mcp` | 平台数据源 | 宿主调 MCP `tools/call`；MCP 不可用时退回读同一份数据文件 |
| `file` | 用户自有表格 | 粘贴 / 上传 CSV、TSV、JSON |
| `webhook` | 消息入站 | `POST /api/inbound` |

**为什么值得这么抽**：引擎只认识五张表（订单 / 退款申请 / 商品规格 / 物流 / 工单），不认识任何平台。新增一个平台 = 加一条声明 + 放一份数据（或换成真实 API 调用），`agent.ts`、`reviewer.ts`、`auth.ts`、界面全部零改动。这与 `tool-registry.json` 是同一个思路——**声明驱动，代码只做收口**。

### 2. MCP 是真连的，不是装饰

- `mcp/server.mjs`：零依赖 stdio MCP 服务端，换行分隔 JSON-RPC 2.0，实现 `initialize` / `tools/list` / `tools/call`，工具面由声明派生（当前 9 个工具，命名空间前缀 `commerce.`）。
- `desktop/server.mjs`：启动时 `spawn` 该子进程，完成 `initialize` → `notifications/initialized` → `tools/list`，把服务器名、版本、工具清单如实反映到界面。点「拉取数据」= 真发 `tools/call`。
- **握手失败不假装**：MCP 起不来时，界面标成「本地文件通路」并给出原因，取数退回读同一份数据文件（同一份数据、同一处校验），不生成假数据。
- 单文件版 `demo.html` 没有子进程，同样如实标注。

**分层**：MCP 只负责「把数据交出来」，**校验与合并一律由 `src/ingest.ts` 做**——数据源无权决定口径，这是刻意的（Shopify 也是把 merchant 侧的写动作排除在连接器之外）。

### 3. 导入的校验口径：不吃默认值

`parseDelimited`（手写状态机，支持 `"` 包裹与 `""` 转义、自动判分隔符、去 BOM、CRLF 归一）→ `coerce`（按列定义做数值 / 布尔 / JSON 强转）→ `mergeRows`（按主键 upsert）。

拒绝规则（返回行号与原因，**不补默认值、不静默跳过**）：

- 主键列为空；
- 该是数字的列不是数字；
- 该是布尔的列不是布尔；
- 该是 JSON 的列不是合法 JSON。

实测：`qty=abc` 与空 `order_id` 两条被拒，库内条数不变；同一份数据重复导入是「更新 N 行、新增 0 行」。

### 4. 运营侧的两个细节

- **GBK CSV**：中文 Windows 下 Excel 导出的 CSV 多是 GBK。前端先按 UTF-8 解，出现替换字符就换 `TextDecoder("gbk")` 重解——不让使用者自己去转格式。
- **入站去重**：微信侧重复推送是常态，`msg_id` 相同直接记为「已去重」并返回，不跑第二遍。

## 三、界面决策（本次改版）

| # | 决策 | 理由（对应用户反馈 / 对标） |
|---|---|---|
| 1 | **删掉说明书式首屏**（「给谁用 / 怎么用 / 自主边界」三卡 + 「三条真实场景」块 + 右上角 `?` 帮助弹层） | 成熟产品不用告诉别人自己能做什么。边界说明改到**用得到的地方**：右栏「自主边界」、审批卡里的「批准 / 驳回分别会怎样」 |
| 2 | 首屏改成**工作台**：数据已接入（各表条数，可点）/ 等你拍板（列条目 + 金额）/ 最近的处置（可点进详情） | 首页只回答两个问题：现在有什么、要我做什么 |
| 3 | 左轨新增**数据源**格，独立成页 | 对标项目的 integrations 页；数据接入不该藏在弹窗里 |
| 4 | 连接器卡显示 **badge + 平台 + 数据表规模 + 工具名 + 联通状态 + 拉取按钮** | 「已联通」要说清是几个工具在线；工具名在这里是必要的（要配置时得知道调什么） |
| 5 | 导入面板**内置示例数据**（一键填入一行） | 让「导入 → 看到新增/更新/拒绝」这件事三十秒内发生 |
| 6 | 顶栏引擎标识**可点切换**「智能模型判定 / 内置规则判定」 | 大模型判定一条 20–30 秒。演示不该被网络和延迟绑架，但也不能假装是模型判的 |
| 7 | 输入区提示行从「Agent 会自动完成：理解需求 → 核实订单 → …」压成一行按键提示 + 数据源入口 | 同一类说明书话术，压缩到不占注意力 |
| 8 | 术语卫哨的扫描范围**排除 `<code>` 内的工具名与接口地址** | 数据源页上的 `commerce.orders_list`、`POST /api/inbound` 是集成标识，属于必要信息；卫哨改为只在业务视图上零容错 |
| 9 | 重新打开页面时，队列与五档指标**接着上一轮**：入站流水里带处置结果的最近 8 条回灌成会话（服务端版） | 自检发现的反例：流水里有 4 条「已处置」，指标却是「0 已自动处理」——同一屏两句话互相打脸。宁可多存一点，也不要首页自相矛盾；更早的条目只留流水，不把 40 条完整轨迹都塞进响应。单文件版没有服务端可回灌（一切在页内内存，刷新即重置），但入站判重口径已与服务端对齐 |

## 四、实测结果（2026-10-15，真实 Chromium）

| 断言 | 结果 |
|---|---|
| MCP 握手 | `initialize` 返回 `commerce-connectors 1.0.0`，`tools/list` 9 个工具 |
| 连接器拉数（走 MCP） | 订单中台 +4 / 售后工单 +4（退款 2 + 工单 2）/ 物流轨迹 +4 / 商品规格 +3，拒绝 0 |
| 幂等复拉 | 同一连接器再拉一次：新增 0、更新 4 |
| 导入校验 | 首次「新增 1 行」；重复「更新 1 行」；脏数据「拒绝 2 行」并给出行号与原因 |
| 导入即刻生效 | 拉进来的订单（O20260912-3301，¥268 色差）随即被一条新客户消息用上，走完六步并自主完成退款 |
| 微信入站 | 唯一消息 → `handled` + 客户回复可复制；同 `msg_id` 再投 → `deduplicated`，队列不新增 |
| 刷新接续（本版新增） | 投一条 → 刷新页面：`st.sessions = 1 / st.inbound = 2`，指标仍「1 已自动处理」、队列仍 1 条、点回去六步全还原（steps=6）。单文件版刷新即重置（无服务端可回灌），但同一条消息连投三次 = 1 条已处置 + 2 条已去重 |
| 入站转审批 | 门卫代收的破损案 → 停办，审批卡「单号 20261015-02 / ¥1,299.00」 |
| 审批闭环 | 点指标「待人工审批」→ 进审批中心（筛选标签出现）→ 批准 → 「已按「升级人工审批」放行并完成处置」，指标回到「已自动处理 1」 |
| GBK 文件 | 249 字节 GBK CSV 读入后「天猫 / 微信小店」正常，无替换字符 |
| 指标点击回归 | 「已自动处理」筛选 1 条 + 标签；「清除筛选」恢复全量 |
| 工程术语卫哨 | 工作台 / 数据源 / 处置页 / 入站后 多视图 **clean** |
| 单文件版 `demo.html` | 263.6 KB（新增人工跟进台账后重建；此前 247.9 KB），17 模块内联；工作台、连接器（如实标「本地文件通路」）、拉数、导入、入站处置、人工跟进全部复测通过，无引擎错误。**前端三处升级后为 278.3 KB**（见 `docs/04` 第九节）；**「去跟进」跳转收敛后为 283.8 KB**（见 `docs/04` 第九节第 6 条与交付说明四·19）；**新增接口设置页后为 303.2 KB / 310,465 字节**（见交付说明四·20 与 `运行证据-接口设置页-2026-10-21.txt`） |
| 回归门禁 | `--gate --offline` **8/8 符合期望，退出码 0** |

## 五、踩到的两个真实坑（留给后来人）

1. **HTTP 服务端异常必须留痕**。最初只回一句 JSON `{ok:false,error}`，排查时无法区分「请求没到」还是「处理时炸了」。现在 `desktop/server.mjs` 在兜底 catch 里 `console.error` 出方法与路径。
2. **表单值不要只信状态镜像**。原实现让 `<textarea>` 的 `input` 事件写进 `st.xxx`，提交时读 `st.xxx`；一次重渲染与一次合成事件交错就会「明明框里有字，提交说空」。改成**提交时以 DOM 当前值为准**，状态只用于回填。
