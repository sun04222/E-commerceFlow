# 02 · 架构与核心对话流程

> 本文说明工程怎么分层、一条咨询在系统里怎么流动、以及四个关键机制的判定逻辑。
> 所有图都是 ASCII，任何编辑器可直接读；图中每个框都能在 `src/` 里指到文件。

## 一、总体架构（五层）

```
┌──────────────────────────────────────────────────────────────────────┐
│ 入口层   src/cli.ts                                                   │
│   --demo  --ask  --case  --gate  --ablation  --violation-demo         │
│   退出码契约：0 成功｜1 门禁未过｜2 用法/模型通道错误                    │
├──────────────────────────────────────────────────────────────────────┤
│ 编排层   src/agent.ts  ·  runCase(msgId, deps, opts)                  │
│   受理 → 分类 →〔clarify 分支〕→ 取证 → 判责 → 只读复核 → 审批 → 结单   │
│   首轮取证刻意保守（orders+refunds+logistics），给 Reviewer 留出拦点    │
├──────────────────────────────────────────────────────────────────────┤
│ 能力层（全部确定性逻辑，与模型无关）                                    │
│   tools.ts    工具面：命名空间 / 按环节装配 / invoke / 快照             │
│   auth.ts     三档授权 + 审批回调回路                                   │
│   reviewer.ts 只读复核：A1-A5 取证与事实 + B 组 SOP 阶段合规            │
│   context.ts  三层渐进式披露        trace.ts  决策轨迹 JSONL            │
├──────────────────────────────────────────────────────────────────────┤
│ 领域契约层（数据即规则，改契约不改代码）                                │
│   data/sop.json          五环节 + 六种案件类型（路径/证据/资金动作）     │
│   data/policy.json       字段口径 / 金额规则 / 一致性规则 / 阶段规则     │
│   data/tool-registry.json 8 个工具的声明式注册表                        │
├──────────────────────────────────────────────────────────────────────┤
│ 数据层（全部合成，带 _notice 标注）                                    │
│   messages  orders  refunds  sku_specs  logistics  tickets             │
│   入口是「客户的一句自然语言」——这是售后 agent 与退款核对工具的分界      │
└──────────────────────────────────────────────────────────────────────┘
                    │
                    ▼  文本环节（可替换，故障不静默降级）
              src/llm.ts（全工程唯一一处模型调用）
              understand / judge / reply 三个环节可切模型；
              密钥不可用 → --offline 规则占位（judge_source=offline_rule）
```

**分层的核心原则：能力层不依赖模型，模型只承担三个文本环节。** 所以密钥失效时，工具面、装配、授权、复核、轨迹照常端到端跑通并被回归门禁校验——本工程的全部验证正是在 `--offline` 下完成的。

## 二、核心流程：一条咨询的完整旅程（以 M01 为例，真实轨迹 20 行）

```
客户：「我8月8号买的那把椅子，颜色跟图片差太多了，我要退钱。」
  │
  ├─① 受理 accept ───────────────────────────────────────────────
  │    understand：关键词「退钱」→ REFUND_ONLY；日期 8月8日 + 商品词「椅子」
  │                → 解析出订单 O20260808-1107；情绪 unhappy
  │    classify ：SOP 定义 → full 路径，要求五源证据，资金动作 decide_refund
  │
  ├─② 取证 investigate ──────────────────────────────────────────
  │    assemble(tools,"investigate") = 5 个只读工具（无可执行工具，断言保证）
  │    首轮保守集 = 要求证据 ∩ {orders, refunds, logistics} = 取 3 源
  │    ··· 刻意保守：给 Reviewer 留出真实可拦的对象 ···
  │
  ├─③ 判责 judge ────────────────────────────────────────────────
  │    三层上下文披露：摘要层✓ / Schema层✓ / 字段级契约✓
  │    判据归纳：C1 可退上限=389+0｜C2 申请 389 未超上限｜C3 已本人签收｜C4 工单已核验
  │    决策 REFUND｜金额 389
  │
  ├─④ 只读复核 review ───────────────────────────────────────────
  │    A1 取证完整性：缺 sku_specs + tickets → REJECT_MISSING_EVIDENCE
  │       + 补查计划（护栏：只能含 aftersales.query_* 只读工具）
  │    ⇒ 补证一轮 → 重判 → 再审：A1-A5 全过 → PASS
  │
  ├─⑤ 审批 approve ──────────────────────────────────────────────
  │    assemble(tools,"approve") = 5 只读 + 3 动作工具（装配发生变化，入轨迹）
  │    授权分档：资金类 389 → >100 且 ≤500 → ASK（执行前询问）
  │    审批回调：交回宿主 → 脚本确认 → 回写 approver/decision/at
  │    ⇒ 放行并执行 aftersales.decide_refund
  │
  └─⑥ 结单 close ────────────────────────────────────────────────
       customer_text：「您的退款已处理完成，退款金额 389 元……」
       internal_note ：「授权闸放行并执行 aftersales.decide_refund，金额 389。」
       全程 20 行 JSONL 落盘 runs/M01-*.jsonl
```

## 三、四个关键机制的判定逻辑

### 3.1 授权分档树（src/auth.ts）

```
                    ┌─ 只读工具？ ──是─▶ AUTO（任何模式都允许，不改变状态）
                    │
工具进入授权闸 ──────┤─ 资金类动作？ ──否─▶ ASK（换货建单/退货运单：不可逆，需一次人工确认）
                    │
                    └─ 是 ─▶ 按金额参数动态分档
                            ≤100  ─▶ EXECUTE（直接执行）
                            ≤500  ─▶ ASK    （执行前必须取得一次人工确认）
                            >500  ─▶ APPROVE（Agent 无权执行，挂起等人工审批，
                                              连「自动确认」这条路都不给）
```

关键性质：**同一把工具，不同金额落入不同档位**——授权策略跟随参数动态升级，不是工具级的静态白名单。

### 3.2 Reviewer 裁决树（src/reviewer.ts）

```
                      ┌─ A1 取证完整性 ─缺─▶ REJECT_MISSING_EVIDENCE（可恢复：给补查计划）
                      │
                      ├─ A2 金额口径 ─超限─▶ REJECT_AMOUNT        （applied > paid + fee）
                      ├─ A3 事实一致性 ─冲突─▶ REJECT_FACT_CONFLICT（如「未收到货」但已签收）
   review(input) ─────┤
                      ├─ A4 判据留痕 ─为空─▶ REJECT_NO_CRITERIA   （结论不可回放）
                      ├─ B  SOP 阶段合规 ─▶ REJECT_STAGE_VIOLATION（诉求不明闯进取证/判责）
                      ├─ A5 模糊例 ──────▶ WARN_AMBIGUOUS         （无确定口径，只告警不阻断）
                      └─ 以上皆无 ──────▶ PASS
   最终裁决 = 所有 finding 中 severity 最高者（刻度见 reviewer.ts 顶部注释）
```

Reviewer 的**结构性约束**：输入只有「已取到的数据 + 已走完的环节」，手里没有工具句柄——它不可能执行任何操作，只有两种权力：驳回、要求补证。补查计划还有第二道护栏：出现非 `aftersales.query_*` 的工具直接抛错。

### 3.3 补证回路（为什么首轮刻意保守）

```
首轮取证（保守集）──▶ 判责 ──▶ Reviewer 复核 ──缺证据──▶ 按补查计划补证 ──▶ 重判 ──▶ 再审
                                    │                                              │
                                    └── 仍缺/仍冲突 ──▶ 硬阻断，授权闸不会放行 ◀──────┘
```

真实场景里首轮计划可由模型产出，机制不变：**取证是否完整，不由取证者自己说了算**。

### 3.4 诉求不明的 clarify 分支（SOP 硬规则）

```
case_type = UNCLEAR
   │
   ├─ 正常路径：只追问（生成澄清问题），不进取证与判责
   │            Reviewer 确认合规 → CLARIFY_NEEDED
   │
   └─ 负向验证（--violation-demo 强行绕过）：
        Reviewer 检出「实际走过 investigate → judge」
        → REJECT_STAGE_VIOLATION（severity 最高）→ 授权闸阻断
```

## 四、装配随环节变化（工具可见性即安全边界）

| 环节 | 可见工具 | 说明 |
|---|---|---|
| accept（受理） | 无工具 | 理解与分类是纯文本环节 |
| investigate（取证） | 5 个只读查询 | 装配里结构上不存在可执行工具 |
| judge（判责） | 5 个只读查询 | 判责不执行，只归纳判据 |
| approve（审批） | 5 只读 + 3 动作 | `create_return_label` / `create_exchange` / `decide_refund` 到此才可见 |
| close（结单） | 5 个只读查询 | 回执生成不碰动作工具 |

轨迹里的 `plan` 行会记录每个环节的装配结果与「新增了哪些工具」——装配变化本身是可审计的。
